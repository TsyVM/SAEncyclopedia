# Chapter 40 — The Render Pipeline: `CRenderer`, the Four Visible-Entity Lists, and the Pass Order

> **Goal of this chapter:** decode how San Andreas turns "the world" into "a frame." Every visible thing is
> first sorted by `CRenderer` into **four fixed pointer arrays** — invisible, super-LOD, LOD, and full
> visible entities — which pack **end-to-end in memory** and run straight into their four count variables.
> Those lists are then walked by an ordered sequence of render passes (`ScanWorld` → `ConstructRenderList`
> → `RenderRoads` → `RenderEverythingBarRoads` → `RenderFadingInEntities`). This chapter proves the list
> sizes by the tiling they force, reads the pass order out of the exe, and shows the pipeline is driven by
> the [C39](../C39-Camera/C39-Camera.md) camera and frames the [C38](../C38-Skybox-And-Clouds/C38-Skybox-And-Clouds.md) sky.

## 40.1 Why the tiling is the whole proof

The four render lists are declared in `gta-reversed` with sizes 150, 50, 1000, 1000, but this chapter does
not adopt those numbers — it *earns* them. The four array base addresses are fixed globals, each one
referenced directly by the render code (so they are real, located memory, not guesses). The only way those
particular addresses can pack end-to-end — each array's base landing exactly where the previous array ends,
and the last one ending exactly at the count block — is if the counts are 150, 50, 1000, 1000. Any other
count leaves a gap or an overlap. So the tiling **is** the size proof, in the identical standard C20 used to
prove an audio pack tiles its file and C31 used to size a slot table: `count × width` with no residue,
here applied to four arrays laid consecutively in the executable's `.bss`.

## 40.2 The shape of a San Andreas frame, in one paragraph

The [C39](../C39-Camera/C39-Camera.md) camera fixes the view. `CRenderer::ScanWorld` walks the
[C5](../C5-CWorld/C5-CWorld.md) world sectors the camera can see and collects candidate entities;
`ConstructRenderList` reads the camera matrix (`0xB6F03C` — the very field
[C38](../C38-Skybox-And-Clouds/C38-Skybox-And-Clouds.md) and [C39](../C39-Camera/C39-Camera.md) also use) and
sorts those candidates by distance into the four lists — full-detail entities near you, LODs and super-LODs
for the far city, and an invisible list for things that must be processed but not drawn. Then the passes run
in order: the sky gradient goes down first (C38, no depth write), `RenderRoads` lays the road network,
`RenderEverythingBarRoads` loops `ms_nNoOfVisibleEntities` and draws the rest, and `RenderFadingInEntities`
handles the streaming pop-in alpha. Effects, particles and the HUD ([C23](../C23-Fonts-HUD/C23-Fonts-HUD.md))
finish the frame. Every one of those steps is a named function at a known address, and the lists they share
are the four arrays this chapter sizes.

## Key takeaways

- `CRenderer` sorts the world into **four** `CEntity*` lists — invisible (150), super-LOD (50), LOD (1000),
  visible (1000) — and their sizes are **proven by the tiling**: they pack from `0xB745D8` straight into the
  count block at `0xB76838` with no residue.
- The pipeline is an ordered pass sequence (`ScanWorld` → `ConstructRenderList` → `RenderRoads` →
  `RenderEverythingBarRoads` → `RenderFadingInEntities`), each pass setting render states and walking a count.
- It is driven by the [C39](../C39-Camera/C39-Camera.md) camera (the matrix at `0xB6F03C`) and frames the
  [C38](../C38-Skybox-And-Clouds/C38-Skybox-And-Clouds.md) sky — three rendering chapters that reference the
  same camera global, cross-checking each other.
