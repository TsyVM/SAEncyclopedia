## Why this is a real verification

[C27](../C27-Function-Catalogue/C27-Function-Catalogue.md) was explicit that its names were only as
trustworthy as the external `gta-reversed` match until checked against the file, and it checked just 13 by
hand. The obstacle was labour: reading 355 disassembled bodies one at a time is slow. C28–C36 removed the
obstacle without lowering the bar. Each of those chapters pinned a set of **class-private static addresses** —
`CGarages`' pool at `0x96C048`, `CStreaming`'s streaming-info array at `0x8E4CC0`, `CPathFind`'s node tables,
and so on — addresses that essentially only that class's code touches.

So there is now a cheap, strong test for a name: **does the method named `CGarages::something` actually read
or write the garage pool?** If yes, the external label and the machine code agree on which subsystem the
function belongs to, and a wrong label would have to *coincidentally* manipulate exactly the class it was
mislabelled as — a far higher bar than a plausible-looking name. This is the same standard
[C27.3](../C27-Function-Catalogue/03-verification-and-the-remaining-124.md) used ("the code does what the
name says"), narrowed to the part that is mechanically checkable at scale: *the code operates on the right
class's data.*

It is worth being precise about what this is **not**. It is not the same as C33. C33 took an *unnamed*
function and *inferred* a class from the data it touches — a new claim. C37 takes an *already-named* function
and *confirms* the name against the data — a check on an existing claim. The signature map is identical; the
direction is opposite. C33 grows the named set from below (attributing the unknown); C37 hardens it from
within (verifying the known). Neither invents a method name.
