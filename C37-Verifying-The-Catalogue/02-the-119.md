## 2. Three spot-checks

To confirm the promotions are genuine (the method really operates its class's data), three were disassembled
in full:

- **`CStreaming::RemoveLoadedZoneModel`** (`0x0040B340`) reads the streaming-info array at `0x8E4CC0` and
  unlinks a model from its zone list — streaming-info work under a streaming name.
  ([C28.3](../C28-Class-Catalogue/03-cstreaming-and-rederiving-c2.md))
- **`CGarages::DeActivateGarage`** (`0x00447CB0`) does `imul …,0xD8; add …,0x96C048; or byte [+0x4E],2` —
  it sets the garage's flag bit in the garage pool, exactly the class its name claims.
  ([C29.2](../C29-Gameplay-Object-Pools/02-cgarages-the-garage-pool.md))
- **`CVehicleRecording::RemoveAllRecordingsThatArentUsed`** (`0x0045A160`) walks the 16-byte recording table
  from `0x97D884` — recording-table work under a recording name.
  ([C34.1](../C34-Vehicle-Recording/01-the-recording-table.md))

In each the referenced static is used *as* the structure its source chapter proved it to be, so the name and
the bytes agree.

## 3. Why 76 stay 🔷 — and it isn't a refutation

The test is deliberately conservative, so a non-promotion means "not confirmed *by this test*," never
"disproven." A 🔷 method in a structured class can fail to touch a signature static for ordinary reasons:

- **It works through a helper.** Many small methods call a shared accessor (`GetAt`, a pool getter) that
  holds the base address, so the caller's own body never names it. The data flows through a `call`, invisible
  to a static-address scan.
- **It uses the object's non-signature fields.** A method may read a member the structural chapter didn't
  pin as a signature (a flag byte at some offset, a `this`-relative field), which is real class work but not
  on the short list of fingerprint addresses.
- **It is a query/predicate with no data reference at all** — e.g. reads only its arguments, or a single
  boolean global the chapter never called a signature.

None of these make the name wrong; they make it *unverified by the cheapest test*. Those methods keep their
🔷 and remain candidates for a manual read (the [C27.3](../C27-Function-Catalogue/03-verification-and-the-remaining-124.md)
route) or for promotion by a future chapter that pins more of their class's fields as signatures — the same
"grows with the encyclopedia" property [C33.2 §4](../C33-Attributing-The-Unnamed/02-the-eleven-and-what-remains.md#4-why-109-dont-resolve--and-thats-a-result)
noted for the classifier.

## 4. What the pair (C33 + C37) achieves

Together the two chapters turn C28–C36's structural work into a lever on C27's catalogue from both sides: C33
attributed **11** of the 124 unnamed to a class, and C37 verified **119** of the named — 130 functions gained
a firm class footing from the *same* signature map, none of it adopting an external name as truth. The
catalogue is no longer "368 names, 13 checked"; it is "368 names, 132 verified by the file, 11 more
attributed, and a repeatable method that improves every time another class is structured."
