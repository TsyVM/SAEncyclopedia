# Chapter 38 — The Skybox That Isn't: Sky Rendering, Clouds, Moon and Stars

> **Goal of this chapter:** answer a rendering question with the same byte-level discipline the data-file
> chapters use. GTA:SA has no skybox *texture* and no skybox *mesh*. The sky is an **untextured, four-vertex
> Gouraud gradient** drawn edge-to-edge behind the world, its top and bottom colours supplied every frame by
> the timecycle ([C15](../C15-Timecycle/C15-Timecycle.md)). Everything else you see up there — clouds, the
> moon, the star field, moving fog, the rainbow — is a small number of **sprites from `particle.txd`**,
> placed by fixed tables inside `CClouds`. This chapter reads those functions and tables straight out of
> `gta_sa.exe`.

## Deep-dive pages

- [C38.1 — The sky is not a box](01-the-sky-is-not-a-box.md): `SetUpOneSkyPoly` (`0x713060`) builds a
  vertex-coloured quad — top two vertices tinted the sky-top colour, bottom two the sky-bottom colour,
  U=V=0, no raster bound — and `RenderSkyPolys` (`0x714650`) reads the timecyc-derived grey to draw it. The
  cross-subsystem tie to [C15](../C15-Timecycle/C15-Timecycle.md).
- [C38.2 — Four sprites from particle.txd](02-particle-txd-textures.md): `CClouds::Init` (`0x7138D0`) loads
  exactly four textures by name — `cloud1`, `cloudmasked`, `cloudhigh` (+ mask `cloudhighm`) and `lunar`
  (+ mask `lunarm`, the moon) — into four globals. There is no `sky*.txd` in the retail tree; these live in
  `particle.txd`.
- [C38.3 — Stars, fog and volumetric cloud counts](03-stars-fog-volumetric.md): the star field is three
  `float[9]` tables that tile to the byte at `0x8D55EC`/`0x8D5610`/`0x8D5634` with values read straight from
  the exe; 11 stars are drawn (`i < 11`, `i % 9`). Moving fog has **350** slots (`cmp eax, 0x15E`),
  volumetric clouds **180** (🟡).

## 38.0 The result first

| Claim | Evidence |
|---|---|
| The sky has **no texture and no mesh** | `SetUpOneSkyPoly` sets vertex RGBA + position and `U=V=0`; `RenderSkyPolys` sets `rwRENDERSTATETEXTURERASTER = NULL` before drawing. No skybox `.txd`/`.dff` in the tree. |
| The sky is a **vertex-colour gradient** | top two vertices get `(SkyTop.rgb, 255)`, bottom two get `(SkyBottom.rgb, 255)` → hardware Gouraud interpolation fills the band |
| The gradient colours are the **timecyc** columns | `RenderSkyPolys` reads `CTimeCycle::m_BelowHorizonGrey` @`0xB7CB10` (a lerp of `m_CurrentColours.SkyBottom`); the raw tables are C15's `SkyTop`/`SkyBot` @`0xB7BF78`/`0xB7BD50` |
| Sky sprites live in **`particle.txd`** | `CClouds::Init` @`0x7138D0` calls `RwTextureRead` on `cloud1`, `cloudmasked`, `cloudhigh`/`cloudhighm`, `lunar`/`lunarm` |
| Star field = **3 × float[9]**, tiling to the byte | `0x8D5610 − 0x8D55EC = 0x8D5634 − 0x8D5610 = 0x24 = 9×4`; values match, read by `Render` |
| Moving-fog slots = **350** | `cmp eax, 0x15E` in `MovingFog_GetFirstFreeSlot` @`0x713710` |
| Automated checks | **10 / 10**; `tools/derive_sky.py` re-runs them and refuses to write the JSON otherwise |

## 38.1 Why this chapter is honest about its proof standard

Every prior chapter closed with *arithmetic*: a record width is right when `count × width` leaves no
residue. A renderer does not obviously offer that. What it offers instead is **fixed tables** — the star
positions, the low-cloud offsets, the slot counts — and those *do* close: the three star tables pack
end-to-end at 36 bytes each with no gap, and their float values are read directly from the image, not
guessed. Where a number is a pure control-flow constant (the 350-slot fog cap) it is taken from the
*compare instruction itself*, not from a header. Where a count could only be read from `gta-reversed` and
was not re-found as an immediate in the exe this pass (the 180 volumetric-cloud cap), it is marked 🟡 and
listed as such — a smaller set of proven facts over a larger set of borrowed ones, the house rule.

The role of `gta-reversed` here is exactly its role in [C27](../C27-Function-Catalogue/C27-Function-Catalogue.md):
it supplies **names** for addresses. Every *number* in this chapter was read from `gta_sa.exe`. The
function boundaries were found cold, from a `particle.txd` texture-name string pushed inside the loader,
*before* the name `CClouds::Init` was attached to the address.

## 38.2 The CClouds function map

Found by walking outward from the two cloud-texture name strings (`cloud1` @`0x872874`, `cloudmasked`
@`0x872868`), which are pushed 12 bytes apart inside the loader at `0x7138D0`; the surrounding function
boundaries (the `int3`/`nop` padding runs) give the rest.

| Function | VA | Role |
|---|---|---|
| `Init` | `0x7138D0` | load the four sky textures from `particle.txd` |
| `Shutdown` | `0x712FA0` | destroy them |
| `Update` | `0x712FF0` | advance cloud rotation / moving fog |
| `SetUpOneSkyPoly` | `0x713060` | build one vertex-coloured gradient quad |
| `RenderSkyPolys` | `0x714650` | orient to camera, read timecyc colour, emit the sky bands |
| `Render` | `0x713950` | the conductor: sky, low clouds, moon, stars, streaks, rainbow |
| `MovingFog_GetFirstFreeSlot` | `0x713710` | fog pool allocator (holds the 350 cap) |
| `VolumetricClouds_GetFirstFreeSlot` | `0x7135C0` | volumetric-cloud allocator |

## Key takeaways

- The "skybox" in San Andreas is a rendering *technique*, not an asset: a screen-spanning quad with two
  colours at the top and two at the bottom, hardware-interpolated. There is nothing to extract from the
  disc because there is no sky texture — a **negative result**, proven, in the tradition of C20's
  not-the-sample-rate and C22's dead gridref reader.
- Its colours are the timecycle's, so this chapter *consumes* [C15](../C15-Timecycle/C15-Timecycle.md): the
  `SkyTop`/`SkyBot` columns you can see in `timecyc.dat` are the literal top/bottom vertex colours here.
- The moon is a masked sprite (`lunar`/`lunarm`) scaled by a single global `MoonSize` (@`0x8D4B60`, default
  3); the stars are 11 draws over a 9-entry position table. All small, all fixed, all in the exe.
