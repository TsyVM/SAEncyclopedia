## Why this chapter

The SCM chapter ([C18](../C18-SCM-Script/C18-SCM-Script.md)) decoded the *bytecode* — the opcode stream, the
arities, the container. C28.2 found the *object* that runs one thread of that bytecode and measured it at
224 bytes, but a size is not a structure: it says how much memory a script thread costs, not what a script
thread *is*. Everything a running mission thread needs — where it is in the code, where it came back from
after a `gosub`, its 32 local variables and two timers, whether it is a mission or an ambient script — is a
field in those 224 bytes, and `CRunningScript`'s own eleven methods read and write every one of them.

The satisfying part is that the object **tiles exactly**. The local-variable array is 34 dwords starting at
`+0x3C`; `0x3C + 34×4 = 0xC4`, which is precisely where `Init` starts writing the flag bytes; the flag block
runs to `0xE0` = 224. There is no unexplained gap and no field left without a home — the same
arithmetic-that-closes standard the project uses for a file-format record, applied to a live C++ object. And
it resolves a C28.2 loose end: C28.2 found a 4 KB block at `0xA48960` and could say only that it was "the
mission local-variable memory." C32.2 shows the mechanism — the `+0xDC` flag on a mission script makes its
local-variable accessor index that shared block instead of the script's own `+0x3C` array — so the block and
the object are two halves of one design.
