# Chapter 46 — Input Devices: The Pad, the Controller State, and Two Players

> **Goal of this chapter:** decode how keys, mouse and controller become game actions. San Andreas funnels
> every input device into one abstraction — a **`CPad`** holding a **`CControllerState`** of button and axis
> values — and there are exactly **two** of them, `Pads[2]`, one per player. Each pad **double-buffers** its
> state (a `NewState` and an `OldState`) so the game can tell a held button from a fresh press, and a
> **binding layer** maps ~53 abstract actions (fire, jump, accelerate) onto whichever physical key or button
> the player chose. This chapter sizes those structures to the byte, locates the two-player array, and — a
> correction to a common assumption — shows the shipped backend is **DirectInput 8**, not the SDL the
> reimplementation uses.

## 46.1 One abstraction over every device

The elegance of San Andreas input is that nothing downstream knows whether you are playing on keyboard,
mouse or a gamepad. All three feed a single `CControllerState` — a flat block of `int16` values, one per axis
and button — and the whole game reads *that*. A keyboard `W` and a gamepad's up-stick both end up as the same
`LeftStickY` number; the code that makes the car accelerate never sees a key code. This is the input mirror of
the damage chapter's insight ([C45](../C45-Damage/C45-Damage.md)): just as every hazard becomes one
`eWeaponType`, every device becomes one `CControllerState`, so one set of logic handles them all. The device
differences live only at the very edges — the three "PC temp" buffers ([C46.1](01-state-and-pad.md)) where
keyboard, joystick and mouse are read separately before being merged.

## 46.2 Two pads, because two players

There are exactly two `CPad`s because San Andreas supports two-player co-op. `Pads[0]` is the main player
(and the one keyboard + mouse reconcile into); `Pads[1]` is the second gamepad. Everything that reads input
goes through `CPad::GetPad(i)` — `Pads_base + i × 0x134` ([C46.1](01-state-and-pad.md)) — so the same code
serves both players by index. That the array is fixed at two, in a static `.data` slot, is the same
engine-limit pattern as the render lists ([C40](../C40-Render-Pipeline/C40-Render-Pipeline.md)) and the
camera array ([C39](../C39-Camera/C39-Camera.md)): a small fixed count, sized to the byte, not a growable
list.

## Key takeaways

- Every device collapses into one `CControllerState` (**`0x30`**, 24 `int16` axes/buttons); `CPad`
  (**`0x134`**) wraps five of them (live New/Old + three PC temp buffers) plus a small tail.
- There are **two** pads, `Pads[2]` at **`0xB73458`**, one per player, reached by `GetPad(i) = base + i×0x134`
  — proven cold.
- Input is double-buffered for edge detection ([C46.2](02-edge-detection.md)) and abstracted through a
  binding layer ([C46.3](03-bindings-and-backend.md)); the shipped backend is **DirectInput 8**, not SDL.
