## Why this chapter, and why now

C27 answered *what is this function called*. It did so by matching an external reconstruction by address,
then disassembling twelve bodies to show the names were not fantasy. But a name is a label, not a
structure: knowing `0x00464C90` is `CTheScripts::StartNewScript` tells you nothing about how big a script
object is, where the pool lives, or how the index space works. Those facts are in the bytes of the
function, waiting to be read.

This chapter reads them. The method is the same one [C27.3](../C27-Function-Catalogue/03-verification-and-the-remaining-124.md)
used to get a 412-byte `CObject` stride "for free" while confirming `CObjectPool::GetAt` — except here the
structural fact *is* the point, not a byproduct. For each of the three heaviest classes, a handful of
methods are disassembled and the recurring constants read out: an `imul` by the object stride, a fill
loop that names an array's base and bound, a `[reg + disp]` that pins a field offset. Every such fact is
encoded as an automated check in `tools/derive_class_catalogue.py`, which re-disassembles the real body
on each run and refuses to regenerate the JSON if any expected instruction has gone missing — so the
prose in C28.2–4 cannot drift away from the binary it claims to describe.

The strongest single result is a *cross-chapter* one. [C2](../C2-CStreaming/C2-CStreaming.md) derived the
20-byte streaming-info record and the 26,316-entry array by measuring array bounds from the *data* side.
C28.3 arrives at the identical base address (`0x8E4CC0`), identical stride (`0x14`), identical flags
offset (+6), and identical end (`0x9654B6`) from a completely different function — `CStreaming::ClearFlagForAll`'s
byte-clearing loop — with no knowledge of C2's numbers. Two independent functions agreeing on the same
memory layout is the same standard of proof the whole project runs on, applied here to a data structure
rather than a file format.
