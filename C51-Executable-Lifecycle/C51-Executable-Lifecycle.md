## 51.1 Why the lifecycle is the missing spine

The audit ([`AUDIT.md`](../AUDIT.md)) noted the encyclopedia documented subsystems but not the **executable
architecture** — WinMain, init order, the frame loop as one pipeline. That is this chapter. It matters because
*order is correctness*: streaming must update before the render list is built, input must be read before the
scripts that consume it, collision must run before the physics that reacts to it. The per-frame order in
`CGame::Process` ([C51.2](02-frame-loop-and-shutdown.md)) is not arbitrary — it is a dependency topological
sort, and reading it tells you why, e.g., a script that reads a key press sees this frame's input (input is
first) but a ped reacting to a gunshot event sees it a frame late (events are queued). Every "why does the
game do X a frame later" question is answered by this ordering.

## 51.2 The three moments, in one paragraph

**Startup:** the CRT entry at `0x824570` runs the C runtime, reaches `WinMain`, creates the window and the
Direct3D device, brings up **RenderWare** (`RwEngineOpen`/`RwEngineStart` —
[C50](../C50-RenderWare-Reference/C50-RenderWare-Reference.md)), then calls **`CGame::Initialise`**
(`0x53BC80`), which fans out to 142 subsystem initialisers — pools ([C4](../C4-Entities-And-Pools/C4-Entities-And-Pools.md)),
streaming ([C1](../C1-Streaming/C1-Streaming.md)), the world ([C5](../C5-CWorld/C5-CWorld.md)), model info,
audio ([C20](../C20-Audio/C20-Audio.md)), and the rest — in dependency order. **Each frame:** the main loop's
idle handler calls **`CGame::Process`** (`0x53BEE0`), which updates 81 subsystems in the fixed order that
opens `CPad::UpdatePads` ([C46](../C46-Input-Devices/C46-Input-Devices.md)) → `CStreaming::Update`
([C1](../C1-Streaming/C1-Streaming.md)) → zones/clock/weather ([C22](../C22-Map-Zones/C22-Map-Zones.md)/[C15](../C15-Timecycle/C15-Timecycle.md))
→ `CTheScripts::Process` ([C18](../C18-SCM-Script/C18-SCM-Script.md)) → `CCollision::Update`
([C6](../C6-Collision/C6-Collision.md)) → … → `CWanted::UpdateEachFrame` ([C41](../C41-Ped-AI-Tasks-Wanted/C41-Ped-AI-Tasks-Wanted.md))
→ `CPopulation::Update` ([C26](../C26-Ped-Tables/C26-Ped-Tables.md)); then the
[C40](../C40-Render-Pipeline/C40-Render-Pipeline.md) render passes draw the now-updated world and the frame is
presented. **Shutdown:** `CGame::Shutdown` (`0x53C900`) tears the subsystems down in reverse. That is the
whole game, from `main` to `exit`, and every chapter slots into one of those three moments.

## Key takeaways

- The lifecycle is **entry (`0x824570`) → RenderWare bring-up → `CGame::Initialise` (`0x53BC80`, 142 inits) →
  per-frame `CGame::Process` (`0x53BEE0`, 81 updates) → render ([C40](../C40-Render-Pipeline/C40-Render-Pipeline.md))
  → `CGame::Shutdown` (`0x53C900`)** — the spine every subsystem hangs on.
- The **per-frame update order is a dependency sort**: input → streaming → world/weather → scripts →
  collision → AI → population, *then* render — which is why some reactions are same-frame and some are a frame
  late.
- This chapter is the **timeline index** for the whole encyclopedia: it says *when* each documented subsystem
  runs, closing the audit's "executable architecture" gap.
